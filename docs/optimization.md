# 缺陷与优化清单

2026-10-14 对项目做的一次整体梳理。完成一项就打勾，并注明对应的提交。

## 一、缺陷

- [x] **1. 局域网 HTTP 下单机模式无法开局**
  单机模式直接调用 `crypto.randomUUID()`，但手机用 `http://192.168.x.x` 打开时这个接口不可用，一点开局就报错。
  已改为 `app/utils/random.ts` 里的 `randomId()` / `randomHex()`，联机和单机共用。（`2b40689`）
- [x] **3. 本机历史没有上限**
  单机历史和联机历史缓存只增不减，localStorage 写满后连当前这一局都存不下。
  已改为各保留最近 50 场（`MAX_LOCAL_GAMES` / `MAX_ONLINE_GAMES`）。注意：单机记录超过 50 场后，最早的会被永久删除。（`2b40689`）
- [x] **4. 接口返回非 JSON 时报错不可读**
  网关返回 502/504 的 HTML 页面时，用户会看到 `Unexpected token <`。
  现在会提示「服务暂时不可用」；遇到 5xx 时保留这笔操作，可以重试。（`2b40689`）
- [x] **5. CORS 配置没有去空格，且写了两份**
  `"a.com, b.com"` 中第二个域名会匹配失败。现在统一在 `env.ts` 的 `corsOrigins` 里解析，HTTP 接口和 WebSocket 共用。（`a9a1949`）

- ~~**2. 三人局大金、黄金9 的读屏文案与计分不一致**~~ —— 撤回。按规则，两位输家各付一笔，「每人给 X 分，共 2X 分」是对的。

## 二、规则问题

- [x] **三人局普胜、小金的收分人**
  按规则，收分人应该是输家的下家，但现在由输家自己选，服务端也只校验收分人不是本人。
  结论：保持现有功能，不做限制。

## 三、安全与稳定性

- [x] **6. 接口没有限流**
  创建房间可以被刷爆；加入房间只需要 6 位房间号，可以暴力枚举。
  最终方案：同一 IP 每分钟最多创建 5 个房间、加入 10 次，超出返回 429「操作太频繁，请稍后再试」（`apps/api/src/limiter.ts`，`0eb0fd2`）。
  真实 IP 的获取方式：
  - Render：它的代理不过滤客户端自带的 `X-Forwarded-For`，所以改读 Cloudflare 写入的 `True-Client-IP`（`render.yaml` 中设置 `CLIENT_IP_HEADER`）。上线后要实测一次：同一网络连续创建 6 次，第 6 次应被拦；换手机流量后仍可创建。如果所有人都被拦，说明没取到真实 IP。
  - Caddy 部署：`compose.production.yaml` 中设置 `TRUST_PROXY=1`。
  计数存在进程内存里，只适用于单实例（见第 8 条）。
  **线上实测（2026-10-14）**：第一次测试时，电脑被限流后手机流量也被拦。原因是线上 Render 服务不是从 Blueprint 创建的，`render.yaml` 里的 `CLIENT_IP_HEADER` 没有生效，所有用户共用代理的 IP。已在 Render 控制台手动添加该变量，并加上启动警告：生产环境没配置 IP 来源、或配置的请求头不存在时，会在日志里提示（`c85dea9`）。
  **复测通过**：电脑被限流期间，手机流量仍可正常创建房间；伪造 `X-Forwarded-For` / `True-Client-IP` 都无法绕过。
- [x] **7. 数据只增不减**
  保留天数：七天。超过 7 天没有任何操作的房间，连同命令记录一起删除；启动时清理一次，之后每小时一次。已给 `updated_at` 加索引，天数可用 `ROOM_RETENTION_DAYS` 调整（`0eb0fd2`）。
  房间被删除后，服务端返回 `code: room_not_found`，前端随即删掉本机保存的这个房间的凭证；设备上已缓存的历史对局仍然保留。只认这个错误码，接口地址配错导致的 404 不会误删凭证。
- [ ] **8. 不能多实例部署**
  在线状态 `presence` 存在进程内存里，广播也只发给本进程。目前单实例没问题；以后扩容要接 `@socket.io/redis-adapter`，并在部署文档里写明这个限制。
- [x] **9. 没有数据库迁移机制**
  表结构是启动时用 `CREATE TABLE IF NOT EXISTS` 建的，以后改表结构没法平滑升级。
  现在改为按版本号执行迁移（`apps/api/src/migrations.ts`）：
  - 已执行的版本记在 `schema_migrations` 表里，启动时只执行还没执行过的迁移。
  - 原来的建表语句作为第 1 号迁移；线上已有的表不会被改动，只补记一条版本号。
  - 所有待执行的迁移放在同一个事务里，一条失败就整批回滚；用事务级的 advisory lock 保证同一时间只有一个进程在执行，经过 Neon 的连接池也有效。
  - 部署了旧版本代码、数据库里有它不认识的迁移时，只在日志里警告，不阻止启动。
  以后改表结构：在 `MIGRATIONS` 末尾追加一条新迁移，版本号加 1；已上线的迁移不要再改。不能使用 `CREATE INDEX CONCURRENTLY` 这类不能放进事务的语句。
  测试：`test/migrations.test.ts`，覆盖全新的库、旧库升级、失败回滚、并发启动、回滚到旧版本。

## 七、第二轮检查（2026-10-14）

前 18 条处理完后重新通读了一遍代码，又发现以下问题。标「已复现」的都在本地实际验证过。

### 稳定性与安全

- [x] **19. 数据库连接被断开时，API 进程直接崩溃**（已复现）（`bd1b49c`）
  连接池没有监听 `error` 事件。空闲连接被数据库端断开时（Neon 重启计算节点、维护、网络抖动），`pg` 会抛出未处理的 `error` 事件，进程以退出码 1 退出，要等 Render 重新拉起；在线状态和限流计数也会丢失。
  已改为：给连接池加 `pool.on('error')`，只记一条警告日志；断开的连接会被连接池自动丢弃，下次查询重新建立。
  测试：用 `pg_terminate_backend` 从数据库端断开连接池里的空闲连接，服务不退出，之后的请求正常（去掉修复时这个测试会失败）。
- [x] **20. 记分等命令没有限流，请求里的多余字段原样入库**（已复现）（`affec30`）
  一个普通玩家 2.5 秒发了 200 条记分命令，全部成功；每条附带 90 KB 随机字段，`room_commands` 里多了 17 MB。Neon 免费版只有 0.5 GB，写满后所有人都无法记分。
  已改为：
  - 请求体限制在 16 KB（JSON 和表单都是），超出返回 413「请求内容过大」，不往日志里写错误堆栈。
  - 各命令只接受自己用得到的字段，`rules` 里也不能有多余的键，字符串字段最长 64 个字符；不符合的返回 400，不会写进命令记录。
  - 命令按 IP 限流：每分钟 120 次。
  - 每局最多 2000 笔记分，每个房间最多 500 局，超出时提示结束本场或新开房间。
  复测：同样带 90 KB 垃圾字段连发 200 条，全部被拒，一条都没写进去；正常大小的命令连发 200 条，前 120 条成功，之后返回 429，总共只写进 11 KB。
  仍然存在的限制：有人换很多 IP 慢慢刷，还是能占用存储；没有账号体系就没法彻底避免，好在房间闲置 7 天后会被清理。
- [x] **21. 根目录的 `Dockerfile` 没有跟上共享包**（`36a3209` 引入）（`e413d50`）
  `compose.production.yaml` 用的是根目录的 `Dockerfile`（`docs/deployment.md` 里的 `up -d --build`），它没有复制 `packages/shared`，按文档在自己的服务器上构建会失败。Render 和 CI 用的是 `deploy/` 下的两个 Dockerfile，不受影响，所以 CI 没发现。
  已改为：`compose.production.yaml` 改用 `deploy/Dockerfile.api` / `Dockerfile.web`，删掉了重复的根目录 `Dockerfile`，所有部署方式只剩这一套镜像定义。CI 新增一步检查 compose 文件的格式，并确认它引用的 Dockerfile 都存在。
- [x] **22. 读取房间不限流，可以枚举出哪些房间号存在**（`affec30`）
  `GET /api/rooms/:code` 对不存在的房间返回 404，对存在但没有凭证的返回 403，而且不限流。这样不用消耗加入次数就能扫出所有正在等人的房间，第 6 条给「加入」限流的目的就落空了。
  已改为：读取房间、读取历史局、发送命令时，「房间不存在」和「凭证不对」这两类失败按 IP 计数，每分钟超过 20 次后，这个 IP 暂时不能查询任何房间（返回 429）。成功的请求和「只有房主可以操作」这类业务错误不计数，正常使用碰不到。
  凭证不对的 403 现在带错误码 `access_denied`；前端遇到它和 `room_not_found` 一样，删掉本机这份已经失效的凭证（例如房间号被新房间重新使用），不再反复请求。

### 联机体验

- [x] **23. 实时订阅失败后不会自动重试**（`e3307a9`）
  连上 socket 后，如果订阅房间这一步超时（5 秒）或服务端临时出错，页面会一直显示「正在重新连接」，只能刷新页面。socket 本身没断，所以不会再触发重连。
  已改为：服务端订阅失败时返回错误码，`denied`（凭证无效、房间不存在，两者结果完全相同，不能用来试探房间号）不再重试，`unavailable`（例如数据库暂时不可用）和超时按 1、2、4、8、15 秒的间隔自动重试，期间页面只显示「正在重新连接」。重试逻辑在 `utils/subscription.ts`，有单元测试。
  浏览器实测：打开故障开关（读取房间时报错）后重启 API，页面显示「正在重新连接」，没有弹出错误；关掉开关约 12 秒后自动恢复成「实时同步中」，不用刷新，恢复后记分两边同步。
- [x] **24. 联机请求没有超时**（`e3307a9`）
  `useRoom` 的请求没有超时，网络卡住时按钮会一直处于忙碌状态，也没有「重试」按钮，只能刷新页面。（历史页已有 12 秒超时。）
  已改为：请求默认 20 秒超时；进入房间（创建、加入、回到房间）和历史页可能碰上服务冷启动，放宽到 90 秒。超时或断网时提示「网络超时，请稍后重试」「网络连接失败，请检查网络后重试」，不再显示 `Failed to fetch` 这类英文；这笔操作保留下来，可以点「重试这笔操作」。被限流（429）时也保留，可以稍后重试。
  超时改用 AbortController 加定时器实现。顺带修了一个问题：历史页原来用的 `AbortSignal.timeout` 在 iOS 15 及更早的 Safari 上不存在，那里的历史页一直无法更新联机房间。
  浏览器实测：让记分请求卡住不返回，20 秒后出现超时提示和重试按钮；服务端其实已经记上了这一笔，点重试后没有重复记分。
- [x] **25. 本机存储写满时进不了房间，也记不了分**（`e3307a9`）
  `useRoom` 写入房间凭证和待发送操作时没有 try/catch，浏览器存储写满时创建或加入房间会报错，记分按钮点了没反应。（历史缓存已经做了容错。）
  已改为：`useRoom` 里所有存储读写都经过 `utils/storage.ts` 的 `withStorage`，失败时只是刷新后无法自动恢复，不影响当前操作。单机记分仍然要求先存进去再生效（存不进去会提示），这是原来就有意这样设计的。
  浏览器实测：让 `localStorage.setItem` 一律抛出「空间已满」，照样能加入房间、记分。
- [x] **26. 免费实例冷启动时没有提示**（`ed2dbd8`）
  Render 免费实例闲置 15 分钟后会休眠，下一个请求要等半分钟到一分钟，期间只显示「正在准备…」，容易被当成坏了。
  已改为：首页一打开就在后台请求一次 `/api/health`，球友填昵称的这段时间里服务就在启动了。创建、加入、回到房间的请求超过 4 秒还没返回时，按钮下方提示「服务正在启动，第一次打开可能需要半分钟左右，请稍候。」；历史页更新联机记录时也会补上这句提示（`composables/useSlowHint.ts`）。
  浏览器实测：首页加载时发出了唤醒请求；让创建房间的请求晚 7 秒返回，提示在第 4 秒出现，进入房间后消失。
